## 2. 확인한 범위와 한계

- **공개 홈페이지:** File in & Out, Callog의 2개 프로젝트가 노출된다. 공개 Callog에서도 소개문 누락, 잘못된 섹션 링크, 측정 조건의 한계 문구를 확인했다.
- **현재 작업 폴더:** 위 2개와 AI Handoff, 한갓지도 초안을 포함해 총 4개다. 트러블슈팅은 총 10개 슬롯이며, 실제 서술이 있는 항목 6개와 TODO 4개로 나뉜다.
- **직접 확인한 자료:** 프로젝트 원문, 공통 템플릿, CSS, 이미지 파일, nGrinder 캡처 5장, 아키텍처 그림, SVG 설명 그림, 로컬 생성 HTML, 데스크톱·모바일 표시.
- **실행한 검증:** Hugo 로컬 빌드, 기존 구조 검증 스크립트, TOML 구조·이미지 존재·생성 HTML 검사. 빌드와 기존 구조 검증은 통과했지만 콘텐츠 누락을 검출하지 못했다.
- **검증하지 않은 것:** 각 서비스의 전체 구현 저장소, 서비스 회귀 테스트의 실제 실행 결과, 성능 테스트 재실행, 운영 시스템의 장애·보안 검증. ‘자료에 없다’는 말은 ‘구현하지 않았다’는 뜻이 아니다.
- 로컬 Hugo는 0.163.2, 배포 설정은 0.148.0이다. 로컬에서 폐기 예정 설정 경고가 있었으나 빌드는 성공했다. 공개 사이트에서 재확인한 사항과 로컬에서만 확인한 사항을 구분했다.

## 4. File in & Out

### 프로젝트 전체 구성

현재 순서는 대표 이미지 → 소개·역할 → 데모·관측 도구 → 수료 후 고도화 → 기술 스택 → 아키텍처 → 기여 → 기능 설명 → 트러블슈팅이다. 핵심 문제 해결이 상당히 뒤에 나온다. 기능 소개에서는 공유·권한 설정을 자세히 설명하지만, 백엔드 채용 독자가 먼저 보고 싶을 동시 편집 보존 범위와 운영 장애 해결 요약이 앞에 없다.

- `웹소켓 및 백엔드 담당`이라는 역할 요약에 비해 상세에는 프론트엔드·인프라까지 넓은 기여가 적혀 있다. 팀 프로젝트 당시 역할과 수료 후 단독 변경의 경계를 각 사례에서도 명확히 해야 한다.
- `수료 후 127 커밋`, `관측 6종`은 활동량·구성 규모다. 장애 발견 시간, 복구 절차, 실제 검증 결과를 대신하는 성과로 쓰기에는 약하다.
- 아키텍처 그림은 AWS EC2·RDS 중심인데, 수료 후 설명은 OCI ARM64·k3s·Helm·Istio 중심이다. 시점 표기가 없어 현재 운영 구조를 판단하기 어렵다. **팀 프로젝트 당시 / 수료 후 운영**을 구분해야 한다.
- 아키텍처 그림에는 핵심인 Yjs WebSocket 서버와 협업 데이터 경로가 드러나지 않는다. 자신이 책임진 컴포넌트를 별도 색으로 표시하고 문서 변경·저장·알림 경로를 구분하는 편이 낫다.
- `monitoring_note`도 `highlights` 내부에 들어가 실제 설명문이 출력되지 않는다.
- Jaeger 링크에는 **2026-06-18 12:41~13:41 KST**의 고정 `start/end` 값이 들어 있다. `lookback=1h`도 함께 있어 UI의 우선 적용 규칙은 확인하지 않았지만, ‘방문 시점 기준 실시간’이라는 안내와 맞는 링크인지 재검증해야 한다. 운영 대시보드 전체를 보여주기보다 대표 요청의 추적 예시와 읽는 순서를 연결하는 것이 더 설득력 있다.

### 4-1. 동시 편집 데이터 일관성

**판정: 차별화할 수 있는 주제지만, 원인 표현과 해결 범위를 가장 먼저 다듬어야 한다.**

추천 제목: **워크스페이스 동시 편집에서 다른 사용자의 변경이 덮어써지고 화면이 서로 달랐습니다.**

이미 있는 내용은 전체 문서 저장 방식, 전체 렌더링의 부작용, 잠금·LWW·OT·CRDT 비교, 블록별 `Y.Map`, 변경 감지 코드, 협업 GIF다. 부족한 것은 다음과 같다.

1. **DB 저장 형식과 실시간 병합 단위를 혼동한다.** ‘DB에 문자열로 저장했기 때문에 Yjs도 문서 전체를 병합했다’고 단정할 수 없다. 실제로 어떤 공유 타입·키에 전체 JSON을 `set`했는지, 수신·저장 경로가 무엇인지 보여줘야 한다. 최종 스냅샷을 문자열로 저장하는 것 자체가 CRDT 병합을 막는 것은 아니다.
2. **‘CRDT 채택’인지 ‘기존 Yjs 모델 수정’인지 불분명하다.** 원인에서는 Yjs를 사용한 상태로 읽히고 해결에서는 새로 채택했다고 쓴다. 구현 순서를 정리해야 한다.
3. **서로 다른 블록과 같은 블록을 구분하지 않는다.** 제시된 `m.set('data', block.data)`가 일반 JSON 객체라면 그 자체가 문자 단위 공동 편집을 의미하지 않는다. 같은 블록의 같은 필드까지 병합했는지는 `Y.Text` 등 실제 모델·동작으로 확인해야 한다. 이 보고서는 실제 서비스의 데이터 유실을 확정하지 않는다. [Yjs 공유 타입 문서](https://docs.yjs.dev/api/shared-types/y.map)
4. 본문 `diffBlocks`는 remove/update만 싣고, 코드 캡처에는 insert/move도 있다. **추가 처리가 전혀 없는 것은 아니다.** 다만 서로 다른 범위의 코드를 중복 제시하며 어느 경로가 결과 주장에 대응하는지 설명하지 않는다.
5. `block-change-tracking.png`는 실행 추적 결과가 아니라 소스 코드 캡처다. 독자가 원인 관측 자료로 착각하지 않게 구분해야 한다.
6. 해결 부분의 코드만 약 68줄이고 코드 이미지까지 반복된다. 반면 원격 이벤트 반영, 로컬 변경과의 구분, 재진입 방지 등 핵심 연결 설명은 부족하다.
7. ‘동시 추가 유실 없음’, ‘수신 순서가 달라도 수렴’, ‘다중 서버 공유’의 테스트 조건이 없다. GIF는 시연 근거이지 이 모든 속성을 증명하는 테스트 보고서는 아니다.

**원인 3문장에 채울 내용:** 동시 편집 재현 조건과 화면 차이 → 실제 전체 교체 경로 및 전체 렌더링 → 작성 내용 보존과 입력 안정성을 위해 고쳐야 했던 이유.

**해결 3~4줄에 남길 내용:** 기존 공유 구조의 교체 지점 → 블록 ID·공유 타입 설계 → 변경 블록만 적용하는 방식 → 잠금·전체 교체 방식보다 협업 요구에 적합했던 이유. 긴 변환 함수는 상세 코드 링크로 옮긴다.

**추천 그림:** 하나의 전후 비교도. 왼쪽은 사용자 A가 블록 1, B가 블록 2를 수정했는데 전체 문서 저장으로 한쪽 변경이 사라지는 흐름. 오른쪽은 동일한 입력이 블록별 공유 타입으로 들어가 둘 다 보존되는 흐름. 같은 색을 같은 블록에 유지하고, 같은 블록 편집의 지원 범위를 그림 아래 한 문장으로 한정한다.

**추가 검증 제안:** 서로 다른 블록 수정, 같은 블록 동시 입력, 추가·삭제·이동 충돌, 재연결, 변경 수신 순서 변경, 복수 서버 연결. 각 항목에 클라이언트 수·반복 횟수·최종 내용 일치 여부·유실 여부를 기록한다. 이는 새로 수행할 검증 제안이며 기존에 통과했다고 가정하지 않는다.

### 4-2. 워크스페이스 목록 조회

**판정: 수치는 명확하지만, 이벤트 전달 개선과 조회 API 성능 개선을 분리해 설명해야 한다.**

추천 제목: **워크스페이스 목록의 변경 반영이 최대 30초 늦고, 반복 조회 비용이 컸습니다.**

이미 있는 내용은 30초 폴링, 엔티티→DTO 변환 코드, SSE 이벤트, Projection 조회, 페이지 크기 50의 API, 전후 nGrinder 캡처다.

- 표의 100 VU와 캡처의 2분 실행 시간은 확인 가능하다. 테스트 조건이 전혀 없는 사례는 아니다. 그러나 API·스크립트, 데이터 건수, 서버·DB 사양, 사용자별 목록 크기, 페이지 크기, 워밍업, 반복 횟수가 없다.
- **100 VU가 같다는 것만으로 동일 조건이 되지는 않는다.** 전에는 전체 목록, 후에는 첫 50개만 응답했다면 반환한 작업량도 달라진다. 첫 화면 요구사항을 같은 기준으로 충족했는지와 응답 바이트를 함께 적어야 한다.
- 단일 HTTP 조회 부하 시험으로는 SSE 이벤트 지연이나 폴링 제거의 트래픽 절감을 입증할 수 없다. nGrinder 스크립트가 실제 무엇을 측정했는지 확인해 결과 이름을 붙여야 한다.
- `Mean Test Time`이 단일 API 응답 시간인지 여러 작업을 포함한 테스트 시간인지도 스크립트로 확인해야 한다.
- 성능 비교표가 ‘원인 분석’ 안에 있다. 원인에는 SQL 로그·조회 필드·호출 횟수 등 진단 근거를 놓고, 비교표는 결과로 이동하는 편이 논리적이다.
- Projection 쿼리는 실제로 제시되어 있다. 없는 것은 **변경 전 SQL, 조회 컬럼·쿼리 수·응답 크기가 줄었다는 근거**다. N+1 발생 여부는 엔티티 설정과 SQL 로그 없이 단정하지 않는다.
- SSE와 WebSocket·짧은 폴링·Long Polling의 비교가 없다. 알림이 단방향이고 기존 REST 조회를 유지할 수 있었다는 등의 실제 선택 조건을 적어야 한다.
- 목록 정렬은 수정일·생성일만 제시돼 있다. 페이지 이동 중 변경 발생, 같은 타임스탬프, 이벤트 누락 후 재조회에 대한 처리 범위도 밝혀야 한다. 구현 결함으로 확정하는 항목은 아니다.

**추천 그림:** ‘주기마다 무조건 조회’와 ‘변경 이벤트 수신 후 필요한 목록 조회’를 나란히 배치하고, 하단에 DB의 전체 엔티티 조회→필요 컬럼·페이지 조회를 표시한다. **이벤트 지연 / API 응답 시간 / 요청 수**를 서로 다른 측정 지표로 명시한다.

**결과에 추가할 내용:** 기존 API와 변경 API가 각각 수행한 작업, 실제 데이터량, 응답 건수, 응답 크기, SQL 수, 테스트 스크립트 링크. SSE는 별도로 이벤트 발생~화면 갱신 지연과 일정 시간 동안의 조회 횟수를 측정한다. 현재 자료로 확실한 것은 캡처에 기록된 테스트 결과이지 일반적인 확장성 보장이 아니다.

### 4-3. SSE 운영 안정화

**판정: 실제 증상과 원인 연결은 구체적이다. 다만 배제 실험, 연결 단위, 전달 보장 표현을 수정해야 한다.**

추천 제목: **HTTPS 배포 후 SSE가 반복 재연결되고 다른 인스턴스의 알림이 누락됐습니다.**

- 오류 메시지, 두 화면의 중복 연결, emitter 덮어쓰기, 중복 재연결, heartbeat 부재까지 적혀 있어 조사 과정의 재료는 가장 풍부하다.
- **‘QUIC을 꺼도 동일하므로 전송 프로토콜 문제가 아니다’는 결론이 과하다.** 해당 실험만으로 HTTP/2나 프록시의 다른 원인까지 배제할 수 없다. 확인한 사실은 QUIC 비활성화만으로 증상이 해소되지 않았다는 것이다. 원인 교정 후 동일 조건에서 오류가 사라진 기록을 제시해야 한다.
- ‘유저당 연결 1개’는 여러 탭·기기 연결을 허용하는 `(userId, connectionId)` 설명과 맞지 않는다. 실제 의도가 앱 실행 인스턴스/브라우저 탭당 하나라면 그렇게 써야 한다. 그림도 함께 고친다.
- heartbeat 그림 방향은 서버→클라이언트로 바꿔야 한다.
- **15초를 택한 근거**가 없다. 운영 프록시의 idle timeout, 여유 시간, 연결 수에 따른 송신 비용이 선택 근거가 된다.
- `SseHeartbeatTest`, `SseEmitterStoreTest`의 이름만으로 실제 프록시·다중 Pod에서의 종단 간 동작을 검증했다고 볼 수 없다. 단위 테스트와 실제 환경 확인을 분리해야 한다.
- Pub/Sub은 연결된 구독자에게 중계하는 구조이며, 끊긴 동안의 이벤트를 자동 재전달하지 않는다. ‘어느 인스턴스에서도 동일하게 수신’은 정상 연결 상태에서의 주장으로 한정하고 재연결 시 재조회·이벤트 재생 지원 여부를 적는다. [Redis 전달 보장 문서](https://redis.io/docs/latest/develop/pubsub/)
- 단일 연결/중첩 맵/heartbeat/중계의 네 조치를 길게 펼친 반면, 각각 어떤 관측 결과를 해결했는지 전후 대응표가 없다.

**추천 그림:** 기존 전후 구조도를 재사용한다. 연결 요청과 서버 heartbeat의 화살표를 구분하고, ‘탭당 1개’를 정확히 표시한다. 중계 흐름은 같은 그림의 별도 패널로 두고, 구독 중단 시 재전달 범위를 각주로 적는다.

**추가 검증 제안:** 탭 1개/2개, 연결 하나의 오류 후 나머지 유지, 프록시 idle timeout보다 긴 무이벤트 유지, 재로그인, Pod 교체, Redis 구독 중단·복구. Pod 수·프록시 설정·관측 시간·재연결 횟수·수신/누락 건수를 적어야 한다.

## 5. Callog

### 프로젝트 전체 구성

역할, 담당 기능, 쿼리와 캐시 변경, 전후 성능 기록이 있어 현재 4개 중 가장 빨리 대표 사례로 다듬을 수 있다. 그러나 대시보드 사례에 쿼리, 캐시 호출 경로, stampede, 무효화, Valkey 전환이 한꺼번에 들어가 핵심 판단이 분산된다.

- 대시보드 성능을 대표 사례로 앞에 요약하고, 캘린더는 별도 UI 설계 사례로 배치하는 편이 백엔드 지원 목적에 맞는다.
- 팀 아키텍처는 넓은 서비스 구성을 보여주지만 본인의 책임 영역이 표시되지 않는다. 자신이 구현한 API·캐시·스케줄러·SSE 경로를 강조해야 한다.
- Redis/Valkey 비교의 한계를 상세에서 인정한 것은 유지할 요소다. 첫 화면과 카드에도 같은 해석 범위를 적용해야 한다.
- `Redis vs Valkey`라는 하이라이트는 비교 자체를 성과로 삼는다. 제품 선택 이유와 실제 운영 결정이 없으면 실험을 수행했다는 사실에 그친다.

### 5-1. 대시보드 조회 병목

**판정: 대표 사례로 적합하지만, 지표의 해석과 실패 원인 설명이 덜 끝났다.**

추천 제목: **대시보드 통합 조회가 전체·반복 조회와 캐시 미적용으로 평균 11초 지연됐습니다.**

이미 있는 내용은 `findAll()`·반복 조회의 전후 코드, 내부 호출의 AOP 우회, 통합 응답 캐시 키, 버전 무효화, nGrinder 3회 기록과 비교 한계다.

1. **원인을 어떻게 좁혔는지가 없다.** `findAll()`이 있다는 사실과 실제 병목의 크기는 다르다. 쿼리 로그·쿼리 수·호출 추적·캐시 적중률 중 무엇으로 확인했는지 적어야 한다.
2. `IN/COUNT/GROUP BY`를 적용했다고 하지만 변경 후 코드는 Repository 메서드 호출이다. 핵심 JPQL/SQL 1개와 실행 계획 또는 호출 수를 붙이면 주장을 검증하기 쉽다. 모든 쿼리를 나열할 필요는 없다.
3. 쿼리 개선과 캐시를 함께 적용한 결과라는 한계는 이미 올바르게 적었다. 이 상태에서 Redis 단독 개선 효과를 새로 계산하면 안 된다. 원인별 기여도를 말하려면 `기존 → 쿼리만 → 캐시 추가`를 따로 측정해야 한다.
4. **‘동일 키 최초 계산은 한 스레드만’의 적용 범위가 불명확하다.** `@Cacheable(sync=true)`는 캐시 제공자의 지원을 필요로 하며 여러 Pod의 분산 중복 계산 방지를 자동으로 입증하지 않는다. Spring Data Redis 버전, CacheManager/Writer 설정, 동시 miss 검증을 확인해야 한다. [Spring 캐시 동기화](https://docs.spring.io/spring-framework/reference/integration/cache/annotations.html), [Redis Cache 설정](https://docs.spring.io/spring-data/redis/reference/redis/redis-cache.html)
5. 버전 키 무효화는 변경을 누가 받을지, 권한 변경·조직 멤버 변경을 어떻게 반영할지, 이전 버전 캐시가 언제 만료되는지가 핵심이다. 현재 설명에는 해당 범위·TTL·DB 커밋과의 순서가 없다.
6. **Redis 단계에서 남은 오류 16건**의 종류와 원인이 없다. Valkey 단계의 0건이 교체 효과인지, 조건 차이인지 구분할 자료가 필요하다.
7. **2026-09-27 정정:** baseline 캡처의 이름은 `dashboard_noCache_Test`이고 설명은 ‘레디스 적용안한 테스트임’이다. 처음 검토에서 ‘안’을 빠뜨려 읽었다. 위키 원본 이미지와 로컬 이미지를 다시 확인했으며, 이름·설명 불일치라는 기존 지적은 철회한다.
8. 세 기록 모두 약 2분이다. CPU/메모리/Pod/DB 데이터량, 캐시 TTL·시작 상태, 테스트 사용자·키 분포, 반복 실행, p95/p99가 없어 운영 안정성을 일반화할 수 없다. 특히 캐시가 사용자 키를 쓰므로 100 VU가 동일 계정을 반복했는지 100개 계정인지가 중요하다.
9. **Valkey를 최종적으로 선택했는지, 어떤 조건 때문에 선택했는지가 없다.** 조건이 달랐다면 호환성 확인과 채택 근거를 분리해야 한다.

캡처에서 추가로 확인할 수 있는 수치:

| 기록 | VU | 실행 시간 | 실행 테스트 | 오류 | 계산한 오류 비율 |
|---|---:|---:|---:|---:|---:|
| 개선 전 | 100 | 2분 1초 | 785 | 44 | 약 5.61% |
| JPA 개선 + Redis | 100 | 2분 | 10,174 | 16 | 약 0.157% |
| 동일 코드 + Valkey | 100 | 2분 1초 | 12,685 | 0 | 해당 실행에서 0% |

오류 비율은 화면의 Errors/Executed Tests로 계산한 값이며 HTTP 요청별 오류율과의 일치는 테스트 스크립트 확인이 필요하다. `0건`도 해당 표본의 관측 결과이지 무오류 보장이 아니다.

**추천 그림:** 대시보드 요청 한 건을 기준으로 왼쪽은 전수 조회·반복 조회·프록시 우회, 오른쪽은 제한 조회·통합 캐시 HIT/MISS로 그린다. 기존 `redis-valkey.svg`를 단순화해 활용할 수 있다. 성능 표는 그림 아래 별도로 두고, Valkey 호환 전환은 부록 또는 별도 짧은 실험으로 분리한다.

**추가 검증 제안:** 동일한 데이터·리소스·계정 분포에서 cold/warm cache를 분리해 반복 측정한다. 응답 내용 일치, 권한 변경 후 캐시 무효화, 동시 miss 때 DB 계산 횟수, Redis 장애 시 결과도 확인한다. 테스트 시간은 임의로 길게 정하기보다 워밍업·TTL·안정 구간을 충분히 포함하도록 설계한다.

### 5-2. 캘린더 다일정 배치

**판정: 문제와 해결의 그림은 잘 대응한다. 그러나 지금은 설계 변경 소개에 가깝고 검증 기록이 빠져 있다.**

추천 제목: **월간 캘린더에서 여러 날짜의 일정이 중복 표시되고 겹친 일정을 읽기 어려웠습니다.**

- 날짜 셀별 렌더링의 한계와 주 단위 레인 배치가 직접 연결돼 있다. 기존 전후 SVG는 유지할 가치가 있다.
- 발견 계기와 필요성이 빠져 있다. 실제 어떤 일정 조합으로 문제를 발견했고 어떤 사용 행동을 방해했는지 사례가 필요하다.
- CSS만 바꾸는 방식, 기존 캘린더 라이브러리, 직접 구간 배치 중 무엇을 검토했는지 없다. 사용하지 않은 방식을 사용해 본 것처럼 쓰지 말고, 검토한 제약만 적는다.
- 구간 충돌 검사는 있지만 정렬 기준, 주 경계에서의 잘라내기, 종료일 포함 여부, 월 경계 처리가 설명되지 않는다. 인용 코드가 생략본일 수 있으므로 구현 오류로 단정하지 않는다.
- ‘가려지지 않는다’는 문구는 `+N`으로 숨기는 정책과 구별해야 한다. **표시되는 일정끼리 겹치지 않고, 넘친 일정은 추가 목록으로 접근 가능하다**는 식으로 결과를 정의한다.
- Drag & Drop·Hover·클릭을 유지했다고 했지만 이를 확인한 브라우저·입력 장치·일정 시나리오가 없다.
- 작은 화면에서 그림이 약 299px 폭으로 줄어 내부 글자를 읽기 어렵다. 코드도 가로 스크롤을 요구한다. 세로형 그림 또는 원본 확대 링크를 제공하고 텍스트 결론을 함께 둬야 한다.

**추천 그림:** 기존 전후 그림을 간결하게 다듬는다. 동일한 4~5개 일정을 동일 색으로 표시하고, 주를 넘는 일정·겹친 일정·`+N`을 포함한다. 모바일용은 위/아래 패널을 더 단순하게 구성한다.

**추가 검증 제안:** 하루 일정, 일요일~월요일 일정, 월말~월초 일정, 동일 시작·종료일, 일정 밀집, 시간대 변환, Drag & Drop 후 날짜 보존, `+N` 접근, 모바일 터치. 결과는 ‘정상’ 대신 표시 위치·기간·숨긴 수·저장 데이터가 기대값과 일치하는지로 기록한다. 성능 문제가 아니므로 억지로 TPS를 넣을 필요는 없다.

### 5-3. 다중 Pod 스케줄러·SSE

**판정: 기술적 보장 범위가 가장 엄격하게 검토돼야 하는 사례다. 서로 다른 두 문제를 한 항목에 묶었다.**

권장 분리 제목:

- **다중 Pod에서 KPI 스냅샷 작업이 각각 실행되어 중복 저장될 수 있었습니다.** 실제 중복이 관측됐다는 로그가 확보되면 ‘중복 저장됐습니다’로 바꾼다.
- **SSE 이벤트를 만든 Pod와 사용자가 연결된 Pod가 다르면 알림이 전달되지 않았습니다.**

현재 원문은 ‘중복 생성될 수 있고’라고 서술한다. 실제 장애 해결인지, 배포 전에 발견해 예방한 위험인지 구분하는 것이 정확하다.

1. UUID 소유 토큰과 Lua 비교 삭제는 이전 작업이 다른 소유자의 락을 삭제하는 문제를 막는 설명으로 적절하다.
2. **그것만으로 하루 한 번 실행을 보장하지는 않는다.** 10분 TTL을 넘겨 작업하면 다른 Pod가 락을 잡을 수 있다. 작업 종료 후 즉시 락을 삭제하면, 늦게 시작한 동일 회차 작업이 다시 락을 얻을 수도 있다. 같은 회차를 한 번만 저장해야 한다면 실행 날짜·KPI별 고유 제약, 멱등 저장, 회차별 완료 기록 등의 실제 방어를 확인해야 한다. [Redis 락 유효 시간](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)
3. `10분`이라는 TTL의 근거가 없다. 실행 시간 분포, 최악 조건, 갱신 여부, 작업 도중 프로세스가 종료되는 경우가 필요하다.
4. Pub/Sub 중계는 정상 구독 중인 다른 Pod로 전파하는 문제를 해결한다. 구독 단절 중 이벤트 보존은 별도 문제다. 로컬 fallback은 다른 Pod의 사용자에게까지 전달하는 대책이 아니다. [Redis Pub/Sub 전달 특성](https://redis.io/docs/latest/develop/pubsub/)
5. 단일 스케줄러, Kubernetes CronJob, ShedLock 등과 비교해 왜 이 구조를 택했는지 없다. 기존 Redis 사용·운영 복잡도·요구되는 보장 수준 등 실제 기준을 적어야 한다.
6. Pod 수, 실행 겹침, TTL 경계, 실제 저장 행 수, 이벤트 수신 결과가 없다. 시퀀스 그림은 설계 설명이며 검증 결과를 대신하지 않는다.

**추천 그림:** 스케줄러는 Pod A/B→Redis 락→DB 스냅샷의 시간축으로 그린다. 정상 경쟁과 TTL 만료·늦은 시작을 나눠 보여주고, DB 중복 방지가 실제 존재할 때만 표시한다. SSE는 이벤트 Pod→Redis→연결 Pod→사용자의 경로를 별도 사례 그림으로 쓴다. 현재 두 주제를 유지한다면 한 이미지 안에서도 두 패널의 결론을 분명히 분리한다.

**추가 검증 제안:** 복수 Pod 동시 실행, TTL보다 긴 작업, 한 Pod의 지연 시작, 작업 중 종료, DB 재시도, 다른 토큰으로 해제 시도, Redis 중단·복구. 스냅샷은 ‘락 획득 수’뿐 아니라 대상 날짜·KPI별 최종 저장 건수로 확인한다.

Josh의 가이드는 주로 북미 프론트엔드 초기 경력자를 대상으로 한다고 스스로 범위를 밝힌다. 이를 한국 백엔드 채용의 절대 규칙으로 적용하지 않고, 독자 안내·선별 원칙만 참고했다. 또한 위 사이트에 적힌 성과 수치를 독립적으로 감사한 것은 아니다.

### 비교에서 드러난 공통 부족분

1. **발견의 증거:** 느린 화면·로그·쿼리·trace 중 무엇을 보고 문제라고 판단했는지.
2. **선택의 조건:** 요구 성능, 일관성, 비용, 운영 인력, 시간 제약 중 어떤 조건이 대안 선택을 결정했는지.
3. **같은 기준의 전후 비교:** 같은 입력·작업량·환경에서 어떤 값과 행동이 달라졌는지.
4. **개인 소유 범위:** 팀의 전체 시스템과 본인이 설계·수정·검증한 영역의 분리.
5. **남은 한계:** 미지원 충돌, 재연결 중 이벤트, TTL 경계 등 검증하지 못한 조건.
6. **근거까지의 짧은 경로:** 사례별 코드·테스트·원본 보고서 링크. 저장소 홈 링크 하나만으로는 해당 변경을 찾기 어렵다.
7. **빠른 요약:** 기능 안내와 긴 코드를 모두 읽지 않아도 문제·판단·결과를 이해할 수 있는 첫 화면.

외부 사례가 모두 ‘원인 3문장·해결 4줄·그림 1장’을 쓰는 것은 아니다. 그 형식은 이번 사용자의 편집 기준이고, 사실성·선택 이유·근거 연결은 외부 자료에서도 확인되는 방향이다.

## 9. 모든 트러블슈팅에 적용할 편집 규칙

각 항목은 다음 순서로 통일하는 것을 권한다.

1. **제목 1문장:** `[기능]에서 [관측된 문제]가 발생했습니다.` 해결 기술명보다 실패 현상을 먼저 적는다.
2. **대표 그림 1장:** 같은 입력의 전후 구조 또는 실패·해결 경로를 표시한다. 로그·성능 캡처는 추가 증거로 둔다.
3. **문제·원인 3문장:** 첫 문장에 발견 조건과 관측, 둘째 문장에 근거가 있는 원인, 셋째 문장에 사용자·데이터·운영 영향과 해결 필요성을 넣는다.
4. **해결 과정 3~4개의 짧은 문장:** 변경 지점, 비교 대안, 선택 기준, 검증 방식으로 연결한다. 실제 화면의 줄 수는 폭에 따라 달라지므로 고정 줄바꿈보다는 짧은 문장 수로 관리한다.
5. **결과:** 수정 전후를 같은 단위로 비교한다. 수치가 적절하지 않으면 ‘삭제된 연결 때문에 정상 연결도 제거됨 → 자신의 연결만 제거됨’처럼 행동의 차이를 쓴다.
6. **테스트 조건:** 도구·환경·입력/데이터량·동시성·시간/반복·판정 기준·실제 결과·근거 링크를 기록한다. 하지 않은 검증은 ‘미검증’으로 남긴다.
7. **상세 자료:** 핵심 코드·SQL·테스트·commit/PR·전체 보고서를 펼치기 영역 또는 링크로 제공한다. 포트폴리오 본문에는 결론을 이해하는 데 필요한 부분만 둔다.

사용자가 제시한 3문장에 세 역할을 모두 담으려면 현재 ‘문제 상황/원인 분석’을 합쳐 요약하는 편이 자연스럽다. 두 소제목을 유지한다면 문제에는 짧은 재현 조건만, 원인 3문장에는 관측→기술 원인→영향을 넣고 같은 설명을 반복하지 않는다. 대안 비교는 원인보다 해결 과정에 배치한다.

DB 문제가 아닌 사례에 SQL을 억지로 넣을 필요는 없다. 그 사례에서 실제 수정한 공유 데이터 구조, 연결 저장소 키, 재연결 정책, 구간 배치 알고리즘을 구체적으로 보여주는 것이 목적에 맞는다.

### 테스트 조건 최소 기록표

| 유형 | 반드시 기록할 조건 | 전후 결과의 좋은 기준 |
|---|---|---|
| 조회 성능 | 코드 버전, API/스크립트, 데이터량, 응답 크기/건수, 서버·DB 자원, VU/계정 분포, 실행 시간, 워밍업, 반복 | 평균·p95/p99, 처리량, 오류 비율, SQL 수·시간, 응답 내용 일치 |

## 11. 실제 수정 순서

### 먼저: 신뢰성과 표시 정확성

- 첫 화면의 성능 변화 단계를 정확히 구분하고 상세의 측정 한계를 반영한다.
- `features_intro`, `monitoring_note`, 측정 리포트 앵커를 수정한다.
- SSE 화살표, ‘유저당 1개’, QUIC 배제 결론을 교정한다.
- AI Handoff·한갓지도 초안은 본문이 완성되기 전 일반 배포 포함 여부를 명시적으로 관리한다.
- 팀 당시/현재 운영의 아키텍처 시점을 표시한다.

### 다음: 기존 6개 사례의 내용 보강

- 사례마다 발견 로그/캡처, 최종 변경 링크, 테스트 조건을 먼저 수집한다.
- CalLog 대시보드 → File in & Out 목록 → File in & Out SSE → 동시 편집 → 다중 Pod → 캘린더 순으로 정리하면 대표 백엔드 사례를 먼저 확보할 수 있다.
- 그림·3문장 원인·3~4문장 해결·결과·검증 조건의 공통 구조를 적용한다.
- 스케줄러와 SSE처럼 원인과 판정 기준이 다른 문제는 분리하거나 하나만 대표로 선택한다.

### 마지막: 새 프로젝트 공개 수준으로 작성

- AI Handoff는 실제 실패와 복구를 보여주는 사례 1~2개 및 설치·동작 증거를 확보한다.
- 한갓지도는 담당 범위, ‘한적함’의 정의, 추천 검증 기준부터 확정한다.
- 두 프로젝트 모두 존재하지 않는 장애 경험·수치로 슬롯을 채우지 않는다.

## 12. 이번 검토의 산출물

프로젝트 원문·사이트 코드·이미지는 수정하지 않았다. 이 보고서만 추가했다. 기존 미추적 초안과 문서는 그대로 유지했으며 커밋·푸시·배포를 수행하지 않았다.

검토에서 확인한 빌드 성공은 콘텐츠 완성도를 의미하지 않는다. 다음 검수에서는 최소한 TODO 공개 여부, 참조 이미지 존재, 필수 섹션, 실제 출력되는 소개문, 결과 링크를 별도로 확인해야 한다.
