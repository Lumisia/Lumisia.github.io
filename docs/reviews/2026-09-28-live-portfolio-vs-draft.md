# 현재 공개 포트폴리오와 트러블슈팅 초안 비교

확인일: 2026-09-28. 공개 홈페이지와 File in & Out, Callog 상세 페이지를 브라우저에서 확인하고 현재 초안과 비교했습니다. 아래 평가는 편집 제안이며, 실제 사이트에는 반영하지 않았습니다.

**교체할 가치는 있습니다. 다만 현재 초안을 그대로 전체 교체하는 것은 권하지 않습니다.** 초안의 발견 상황과 선택 이유에 현재 사이트의 핵심 구현 설명을 합치는 편이 낫습니다. 현재 사이트는 기술 자료가 부족한 상태가 아니며, 초안은 일부 사례에서 지나치게 압축되어 있습니다.

## 우선 수정할 문제

### 1. 홈에서 전체 성능 개선과 Valkey 전환 효과가 섞여 보입니다

홈에는 처리량이 `7 → 117`로 표시되고 바로 아래에 `Redis → Valkey 재측정`이라는 설명이 붙어 있습니다. 그러나 Callog 상세 페이지의 측정 단계는 개선 전 7.0 TPS, 쿼리 최적화와 Redis 캐시 적용 후 97.3 TPS, 동일 코드의 Valkey 전환 후 117.4 TPS입니다.

현재 배치는 Redis를 Valkey로 교체해서 처리량이 약 16.8배 증가했다는 오해를 만들 수 있습니다. 전체 성과 카드에는 `쿼리 최적화와 캐시 적용`을 표시하고, Valkey 비교를 별도로 강조한다면 `97.3 → 117.4 TPS`를 사용해야 합니다. 성능 수치를 더 크게 보이게 만드는 것보다 개선 원인을 정확하게 연결하는 것이 우선입니다.

### 2. 초안의 Callog 대시보드 설명은 현재 사이트보다 원인 분석이 약해졌습니다

현재 사이트에는 같은 객체 내부에서 호출한 메서드의 `@Cacheable`이 Spring 프록시를 거치지 않아 적용되지 않은 문제와, 외부에서 호출되는 `loadAll()`의 통합 응답을 캐싱한 해결이 있습니다. 현재 구현에서도 통합 응답에 캐시를 적용하고 사용자, 기간, 버전으로 키를 구분하는 구조를 확인했습니다.

초안은 이를 “전체 조회가 느려 캐시를 적용했다”는 수준으로 줄였습니다. 이대로 교체하면 구현을 진단한 능력을 보여주는 설명이 사라집니다. “캐시가 있었는데도 왜 동작하지 않았는지”와 “어느 호출 지점에 적용하도록 바꿨는지”는 원인과 해결 과정에 복원할 가치가 큽니다. 버전 키를 이용한 무효화도 짧게 유지하는 편이 낫습니다.

### 3. 성능 수치가 설명하는 범위를 더 분명하게 해야 합니다

- File in & Out의 API 측정은 목록 조회 구현의 개선 결과입니다. SSE로 바꾼 것만으로 TPS가 32.7에서 192.4로 올랐다고 연결하면 안 됩니다. Projection과 페이지 처리, SSE 알림은 역할을 나눠 설명해야 합니다.
- 페이지 처리로 한 번에 반환하는 목록의 크기도 달라졌다면, 같은 양의 데이터를 더 빨리 처리한 비교와는 다릅니다. 전후 반환 건수는 아직 확인되지 않았으므로 결과는 “목록 API 개선 전후” 범위로 표현하는 것이 적절합니다.
- Callog는 동일 계정의 반복 요청입니다. 시작 전에 캐시를 비웠어도 이후 요청에는 캐시가 재사용되므로, 모든 요청이 캐시 없는 상태였거나 서로 다른 사용자 100명의 실사용을 재현했다고 설명하면 안 됩니다.
- 초안의 측정 조건 한 줄은 이러한 오해를 줄이는 개선입니다. 약 1,000건은 사용자 기억에 따른 대략적인 규모이며, 당시 장비 사양은 본문에 추가하지 않습니다.

### 4. 기존 사이트의 표현 중 실제 변경 범위보다 넓은 부분이 있습니다

- 공동 편집 원인에는 Yjs를 이미 사용했다고 쓰고, 해결에는 CRDT를 채택했다고 씁니다. 핵심 변경은 새 기술 도입보다 기존 Yjs의 공유 단위를 문서 전체에서 블록으로 바꾼 것입니다.
- SSE 결과의 “유저당 연결 1개”는 다른 탭까지 하나로 묶는다는 의미로 읽힐 수 있습니다. 브라우저의 같은 실행 환경에서 연결을 재사용하고, 서버는 여러 연결을 각각 관리한다는 설명이 맞습니다.
- heartbeat를 넣었다는 사실만으로 모든 프록시 환경에서 연결이 끊기지 않는다고 보장할 수는 없습니다. 중복 재연결 방지와 종료된 연결만 정리한 결과를 중심으로 쓰는 편이 더 정확합니다.

## 실제로 얼마나 달라지는가

| 비교 항목 | 현재 공개 사이트 | 현재 초안 | 판단 |
|---|---|---|---|
| 사례 구성 | File in & Out 3개, Callog 3개 | 같은 6개 사례 | 새로운 성과 추가보다 전달 방식 변경 |
| 성능 결과 | 목록 전후 2단계, 대시보드 3단계 | 같은 수치와 결과 이미지 | 수치 자체가 새로 강화되지는 않음 |
| 발견 상황 | 시스템 현상과 구조 설명 중심 | 타인 테스트, 두 브라우저, 더미 일정, 이전 프로젝트 경험 추가 | 본인이 겪고 판단한 과정이 더 잘 드러남 |
| 선택 이유 | 일부는 일반적인 대안 비교 | 단방향 알림, 블록 편집 경험, 구현 여건, 전환 비용 등 구체화 | 초안이 더 설득력 있음 |
| 원인 분석 | AOP 우회, emitter 삭제, 구간 충돌 등 상세 | 3문장으로 압축 | 읽기는 쉬워지지만 핵심 원인을 빠뜨린 사례 있음 |
| 구현 코드 | 두 상세 페이지에 코드 블록 총 21개 | 현재는 편집 사례에 구현 3개와 접힌 테스트 코드 | 줄이는 방향은 좋지만 다른 사례의 핵심 코드까지 없애면 손해 |
| 그림과 결과 자료 | 이미 아키텍처, 흐름도, 기능 이미지, GIF, 성능 캡처 존재 | 사례마다 기능 아키텍처를 먼저 배치 | 자료의 유무보다 일관된 읽는 순서가 개선됨 |
| 측정 조건 | 일부 부하와 시간만 본문에 기재 | 데이터 범위, 동일 계정, 캐시 초기화 등을 한 줄로 제시 | 측정 결과의 해석이 더 명확해짐 |

6개 중 6개가 같은 주제이고 대표 성능 수치도 같습니다. 따라서 내용이 대부분 새로워졌다고 평가할 수는 없습니다. 가장 큰 변화는 독자가 문제를 이해하는 순서와, 본인의 판단을 설명하는 정도입니다.

## 현재 사이트에서 보존할 강점

File in & Out의 수료 후 단독 운영 기록은 보존하는 편이 좋습니다. 배포 환경, 인증과 쿠키 문제, 관측 도구, 회귀 테스트까지 이어지는 설명은 팀 프로젝트를 만든 뒤 실제로 운영했다는 경험을 보여줍니다. 페이지 상단의 역할과 담당 범위 역시 트러블슈팅의 개인 기여를 이해하는 데 필요합니다.

Callog의 쿼리 개선과 캐시 개선, 캐시 저장소 교체를 단계별로 나눈 표도 보존해야 합니다. 현재 상세 페이지가 Valkey의 보편적인 우수성을 단정하지 않는 점은 장점입니다. 초안에서도 “해당 반복 조회 시나리오에서 추가 개선을 확인했다”는 범위를 유지하는 것이 좋습니다.

이미 있는 자료를 새 자료처럼 더 많이 붙이는 것은 효과가 작습니다. 그림은 기능의 전체 흐름을 먼저 보여주되 변경한 구간을 강조하고, 코드에서는 그 구간을 실제로 바꾼 부분만 보여주는 구성이 적합합니다.

## 권장 최종 구성

1. 제목은 기능과 사용자에게 보인 문제를 한 문장으로 표시합니다.
2. 기능 전체 아키텍처 1장 안에서 변경한 부분을 강조합니다.
3. 문제 원인은 발견 상황, 기술적 원인, 해결 필요성을 3문장으로 씁니다.
4. 해결 과정은 실제 수정과 선택 이유를 3~4개 항목으로 요약합니다.
5. 필요한 사례에만 핵심 쿼리나 구현 코드 1~2개를 넣고, 연결된 코드가 필요한 편집 사례는 3개 발췌를 사용합니다.
6. 결과는 사용자에게 보인 문제의 전후 변화와 GIF 또는 측정 캡처로 보여줍니다. 측정이 있으면 조건을 한 줄로 붙입니다.

교체 가치가 있는 범위는 트러블슈팅 본문과 오해를 부르는 성능 요약입니다. 프로젝트 소개, 역할, 단독 운영 기록까지 통째로 새 초안으로 바꿀 이유는 없습니다. 한갓지도는 현재 공개 홈에 없으며, 회원과 보안 사례를 추가하는 것은 기존 6개 사례의 재작성과 별도 가치가 있는 작업입니다.

## 이번 반영

문서 편집 초안에 실제 구현의 수정 연산 추출, 기존 `Y.Map` 갱신, Editor.js 블록 갱신을 연결한 설명을 추가했습니다. 전체 함수로 오해하지 않도록 발췌 범위를 표시했고, 결과 GIF와 기존 테스트 확인 코드는 유지했습니다. 사이트 소스, 커밋, 푸시는 변경하지 않았습니다.

확인한 공개 페이지: [홈](https://lumisia.github.io/), [File in & Out](https://lumisia.github.io/projects/fileinnout/), [Callog](https://lumisia.github.io/projects/callog/).
