# 한갓지도 회원·보안 포트폴리오 사례 검토

검토일: 2026-09-27. 기준: 첨부 회고, `C:/Git/HanGat_Map`의 HEAD `105675f74c1746480a2ed4cdd8f9cc38ff8a25ba`, 로컬 Git 이력 및 저장된 시험 결과. 이번 검토에서 애플리케이션 변경·새 시험·커밋·푸시는 하지 않았다.

## 우선 판정

- Gemini 진단과 AI 코스 후보 사례를 제외하고 회원·보안 경험을 선정한다. 커밋 작성자만으로 개인 담당을 판단했던 이전 후보 선정은 철회한다.
- 문서는 발견 경위와 설계 이유를 상당 부분 제공한다. 현재 부족한 것은 같은 설명의 재수집보다 핵심 동작의 검증 결과와 짧은 전달 구조다.
- 1번은 설계 의사결정이다. 2·3번은 회고상 개발 중 검토·보완 경험이며, 확인되지 않은 운영 사고·공격 피해·재현 결과로 바꾸지 않는다.
- 회고의 축약 코드는 설명용이다. Git에서 확보한 실제 수정 전 소스처럼 제시하면 안 된다.

## 중요한 근거 한계

### 1. 문제 발생 전후 전체를 커밋으로 확인하지는 못했다

`27afae7`(2026-08-28)의 초기 서비스 구현부터 `AuthService`에 잠금 조회, `noRollbackFor = BaseException.class`, 기존 `expiresAt`을 전달하는 재발급이 있다. 따라서 이 커밋의 직전을 ‘동시 발급·폐기 롤백·만료 연장이 모두 발생하던 구현’으로 설명할 수 없다. 직전 AuthService는 구현 전 골격이다.

비밀번호 코드 검증도 `5bdaabe` 이전의 `PasswordResetService`에 이미 `noRollbackFor = BaseException.class`가 있다. 실제 확인 가능한 `5bdaabe`(2026-08-29)의 차이는 코드 검증을 `PasswordResetCodeService`로 분리하면서 롤백 제외를 `InvalidResetCodeException`으로 좁힌 것이다. ‘실패 횟수가 실제 DB에서 계속 0이던 상태를 재현했다’는 결과는 이번 자료에서 확보하지 못했다.

이것은 회고의 경험을 부정하는 판정이 아니다. 커밋 전 검토 과정은 회고에 근거해 서술하고, 커밋으로 확인한 전후 변경과 구분하라는 뜻이다.

### 2. 기존 성공 시험이 핵심 결함 전체를 검증하지 않는다

`backend/build/test-results/test/TEST-com.example.hangat.user.DemoAccountIntegrationTest.xml`에는 2026-09-20 실행 12개, 실패·오류·건너뜀 0이 있다. H2 MariaDB 호환 모드의 Spring 통합 시험이며, 실제 외부 OAuth·메일 발송 시험은 아니다.

[DemoAccountIntegrationTest.java](C:/Git/HanGat_Map/backend/src/test/java/com/example/hangat/user/DemoAccountIntegrationTest.java:86)의 `demoStillDetectsRefreshReplay`는 회전한 토큰을 순차 재사용하면 예외와 다른 토큰의 폐기 상태가 나타나는지 확인한다. 클래스에 `@Transactional`이 있으므로 서비스 트랜잭션 종료 후 별도 조회로 폐기 커밋까지 검증한 시험은 아니다. 동시 요청도 아니다.

현재 시험 소스에서는 실패 횟수의 커밋 후 누적, 5회 실패 뒤 올바른 코드 거절, 동시 재발급, 고정 만료 시각을 직접 검증하는 사례를 찾지 못했다. ‘시험 통과로 모두 해결 확인’이라는 결과 문장은 아직 부적절하다.

### 3. 보안 효과를 서비스 전체로 확대하면 안 된다

- 카카오 연결은 코드 검증 후 기존 계정을 조회하지만, 일반 가입의 [UserService.java](C:/Git/HanGat_Map/backend/src/main/java/com/example/hangat/user/service/UserService.java:29)는 `DUPLICATE_EMAIL`을 반환한다. 모든 경로에서 가입 여부를 숨겼다고 쓰지 않는다.
- Refresh Token 재사용 탐지는 공격 여부의 확정 판정이 아니다. 정상적인 중복 요청도 회전된 토큰을 다시 보낼 수 있다.
- 프론트 공유 Promise는 같은 JavaScript 실행 환경의 요청을 묶는다. 다른 탭·기기 전체를 묶지는 않는다.
- [AuthService.java](C:/Git/HanGat_Map/backend/src/main/java/com/example/hangat/user/service/AuthService.java:156)의 롤백 제외는 코드 불일치 전용 예외보다 넓다. 2번과 동일하게 전용 예외로 좁혔다고 쓰면 안 된다.

## 각 사례의 그림과 검증 조건

| 사례 | 권장 그림 1장 | 우선 필요한 검증 |
|---|---|---|
| 이메일 소유권·OAuth | 브라우저 / OAuth 제공자 / 백엔드 / 메일의 흐름도. 이메일 입력 → 코드 검증 → 기존 계정 확인 → 연결 동의 순서를 강조하고 토큰 전달 경로는 보조 표기 | 동일한 기존 이메일을 입력했을 때 인증 전 응답과 인증 후 연결 안내, 틀린 코드·만료 코드의 거절, 연결 동의 때 재인증 없이 처리되는지 |
| 실패 횟수 보존 | 좌측 일반 런타임 예외: 횟수 증가 → 예외 → 롤백, 우측 전용 예외: 횟수 증가 → 실패 응답 + 횟수 저장. 좌측은 원리 설명용이라고 표시 | 활성 일반 계정·유효 코드 요청 1개로 틀린 코드 5회. 각 서비스 요청 종료 후 새 트랜잭션으로 DB 횟수 확인, 이후 정답도 거절. 다른 예외는 롤백되는지 확인 |
| Refresh Token | 한 토큰이 회전하는 상태도와 동일한 절대 만료선. 이전 토큰 폐기·재사용 시 후속 폐기·새 토큰의 고정 expiresAt을 표시 | 실제 DB에서 동일 토큰 동시 요청, 요청 종료 후 폐기 상태 조회, 재발급 전후 expiresAt 비교, 만료 전후 판정. 정상 중복 요청이 로그아웃으로 이어지는 정책도 기록 |

CPU·메모리 사양이나 성능 TPS는 이 기능 검증의 필수 조건이 아니다. DB 종류, 계정·토큰의 초기 상태, 요청 순서·동시 수, 만료 시점, 관찰한 DB 상태가 핵심이다. 추가 시험은 새로 실행한 날짜의 기록으로 남긴다.

## 포트폴리오 구조 적용

- 공통 순서: 제목 → 해당 흐름을 설명하는 그림 → 문제 원인 또는 설계 배경 3문장 → 해결 또는 선택 과정 3~4줄 → 시험 조건 → 결과.
- 원인 첫 문장: 첨부 회고의 회원 기능 구현·보안 코드 검토라는 발견 맥락.
- 원인 둘째 문장: 이메일 소유권 혼동, 예외 롤백, 토큰 상태·수명처럼 해당 항목의 구체적 문제.
- 원인 셋째 문장: 잘못된 연결 방지, 시도 제한 유지, 세션 수명 제한처럼 해결이 필요한 이유.
- 해결 과정: 확인한 코드 변경 → 적용 범위 → 선택 이유. 다른 대안을 실제 시험한 기록이 없다면 장단점의 설계 비교로 표시한다.
- 1번 결과는 구현된 인증 순서와 정보 전달 범위다. 존재하지 않은 기존 구현을 만들어 전후 비교하지 않는다.
- 2번 결과는 현재 예외 처리와 확인되는 광범위한 롤백 제외 → 전용 예외의 변경이다. 실제 DB 누적 시험 결과는 확보 후 추가한다.
- 3번 결과는 회전 시 기존 만료 시각 전달과 폐기 정책이다. 기존 순차 재사용 시험 결과와 미검증 동시성·커밋 보존을 구분한다.

사이트의 `content/projects/hangat-map.md`는 아직 AI·지도 등 임시 담당 예시와 TODO를 포함한다. 실제 적용 단계에서는 이 담당 설명과 기능 소개도 회원·보안 중심으로 함께 맞춰야 한다. 이번에는 검토 기록만 갱신했다.
